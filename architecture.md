# Architecture Overview

This document gives agents a fast, accurate understanding of this repository's structure and
architectural rules. **`plugins/` is the single source of truth** — installed directories (local `.claude/`, `.agents/`, global `~/.claude/`, `~/.agents/`) are outputs, never authoritative. Update this
document when the plugin count, ADR set, or top-level layout changes.

## 1. What This Repo Is

`agent-plugins-skills` is the **upstream source monorepo** for a cross-platform library of reusable
AI agent plugins and skills. Plugins are authored here and packaged/deployed into target projects or global workstation profiles via Agent Package Manager (APM) or the legacy bridge installer. It is not an application with a frontend and
backend — it is a **plugin ecosystem + package distributor**, consumed by Claude Code, GitHub Copilot, Codex CLI, Antigravity, and other compliant agent frameworks.

**This repo's working directory contains no application/domain data.** Plugins like `portfolio-advisor`,
`tradingview`, `stock-valuation`, and `etf-analysis` that appear in a Claude Code session's slash-command
or agent list are installed **globally** via the Claude Code marketplace (`~/.claude/plugins/cache/`) —
they belong to *other* projects (e.g. an investment-toolkit repo) and expect to run from *that* project's
working directory, not this one. Invoking one of those commands while `cwd` is `agent-plugins-skills`
will fail to find its expected files (e.g. `investment_screener/backend/data/portfolio.json`) — that's
expected, not a bug in this repo. If a session shows an unfamiliar domain-specific command, check `pwd`
before assuming this repo owns it.

Current scale (read from `plugins/` — verify with `find plugins -name SKILL.md | wc -l` and
`find plugins/*/agents -maxdepth 1 -name '*.md' | wc -l` before quoting a number elsewhere;
`plugins/spec-kitty-plugin` was removed 2026-09-05, never part of this count):
- **6 plugins**
- **30 skills** (active SKILL.md definitions across plugins)
- **19 agent definitions** (`agents/*.md` across plugins)

## Approval contexts: production and simulation

The Agentic OS has two segregated approval contexts, not two mandatory agent processes:

| Context | State store | Signing authority |
| --- | --- | --- |
| Production | `context/control_plane.db` | Human key in `context/identity/allowed_signers` |
| Simulation | `context/simulation/simulation_control_plane.db` | Agent key (`test-human@local`) in `context/simulation/identity/allowed_signers` |

`approver_policy.py` stamps database context and binds the first approving key to the task.
Subsequent gates must use that same key. Simulation filename aliases, symlinks and hard links
are refused rather than silently changing approval roles; unknown filenames require human approval.
Production hooks reject aliased or simulation-stamped production databases. Before a production
push, `gate_evidence.py` checks every proof-bearing history transition against its consumed request,
exact signed challenge, human trust anchor and single-key continuity. Missing historical signatures
fail closed, including pre-rollout tasks; they cannot be recreated from unsigned receipts.

The `init` mode of `setting-up-agentic-os` creates or reuses only the simulation key and reports human,
simulation and isolation readiness separately. Human key setup remains a human operation through
the `signing-setup` mode. Simulation tools route explicitly per invocation, without a sticky environment
switch that could silently divert real intake. Source code and references remain plugin-owned;
installed skill copies are deployment outputs.

Trust boundary: SQLite stamps, filenames and role labels are not immutable against an agent with
the human's OS permissions. Complete isolation requires a separately constrained agent runtime and
human-controlled signing/trust infrastructure. A separate account merely existing does not prove
the agent runs under it. Same-account hostile modification remains an explicit deployment risk,
not a claim that database segregation alone resolves it.

## 3. High-Level Flow: Author → Package → Deploy → Run

```
[plugins/<plugin>/skills/*, agents/*, scripts/*]   (authored here, canonical source of truth)
              │
              │  apm_build_pipeline.py
              ▼
[build/staging/ or dereferenced APM package]       (standalone packages, zero symlinks)
              │
              │  apm install [--global] --target claude,copilot,codex,antigravity
              ▼
[Active Runtime Harnesses]
  • Project: .claude/skills/ (Claude) | .agents/skills/ (Copilot, Codex, Antigravity)
  • Global:  ~/.claude/skills/ (Claude) | ~/.agents/skills/ (Copilot, Codex, Antigravity)
              │
              │  consumed at runtime by
              ▼
[Claude Code | GitHub Copilot | OpenAI Codex | Antigravity (agy)]
```

Skills **run from active installed runtime locations** (local project harnesses or global workstation profiles), never from `plugins/` directly — files under `plugins/` are inert until installed. All installed skills are completely self-contained with physical copies of their scripts and references, enabling runtime execution without cross-plugin dependencies.

## 4. Core Components

### 4.1. Package Management (APM)
- `apm install` — Universal cross-client package installation (targeting Claude Code, GitHub Copilot, Codex, and Antigravity).
- `apm install --global "$PWD"` — Installs every plugin listed in the root `apm.yml` in one command.

### 4.2. Plugin: agent-agentic-os
Three self-contained skills, each a router with modes. `running-control-plane` (modes `intake`, `mode`, `health`, `simulator`, `worktree`) owns the `control_plane/` package, `agent_control.py` and the git guards. `setting-up-agentic-os` (modes `init`, `signing-setup`) bootstraps a project and guides the human signing key, and creates the agent's own simulation identity; it uses the control-plane package from its sibling skill. `improving-skills-in-lab` (modes `plan`, `setup`, `loop`, `score`, `log`, `backport`, `memory`) runs the improvement loop: `plan → setup → loop → score → backport → log`. Layer 2 Wiki & Map Debt governance (`distill_playbook`, `audit_map_debt`, `pre-commit-evolution-guard`, and `turn_evolution_guard`) stays with the control plane and the plugin hooks. Three control-plane edges are cryptographic human gates: Gate 1 (`AWAITING_APPROVAL -> APPROVED`), Gate 3 (`WORKTREE_REVIEW` or `MULTI_AGENT_CODE_REVIEW` `-> VERIFY_EXIT`) and closure (any edge into `DONE`). Each declares `requires_cryptographic_proof`: the coordinator halts with `HUMAN_PROOF_REQUIRED` and a pending, content-bound `transition_request` (Gate 3 binds the commit SHA, tracked-diff hash and untracked-files hash; closure also binds the retrospective digest); the human signs it out of band with `ssh-keygen -Y sign` (OpenSSH prompts for the private-key passphrase) via `show-challenge` and `approve-transition`; the signature is verified outside the database write lock and the request is consumed exactly once in the commit transaction. No prompt, typed word, flag, receipt or actor string can authorize these edges, and there is no skip or force-close path. the `signing-setup` mode of `setting-up-agentic-os` creates the key; residual risk (a same-account agent with direct DB or coordinator access) is documented in `plugins/agent-agentic-os/skills/setting-up-agentic-os/references/isolation-setup.md`.

#### Human gates: SSH-signed `transition_request` (CIBA/RAR lineage)
**Why it matters:** the pipeline's guarantees (plan reviewed, code accepted, task closed) hold only if the human decision cannot be forged by the agent that benefits from it. Soft mechanisms (prompts, typed words, skip/force-close flags, `actor='human'` strings, SQLite triggers trusting an actor column) all failed that test, so Gate 1, Gate 3 and closure require a cryptographic proof instead.

**Model:** a `transition_request` (task, edge, occupancy, nonce, 15-minute expiry, content snapshot) is the RAR-style structured authorization; the human's own SSH key is the CIBA-style out-of-band authenticator. The human signs the printed challenge with `ssh-keygen -Y sign`; the coordinator verifies it against `allowed_signers` (namespace `control-plane@agentic-os.local`) before `BEGIN IMMEDIATE`, then re-checks and consumes the request once inside the commit transaction. An external identity provider (real CIBA push) remains a possible future replacement for the local signer.

**Setup:** per machine, by the human, via `setup_ciba_identity.py` (the `signing-setup` mode of `setting-up-agentic-os`). `allowed_signers*` and `context/identity/challenges/` are machine-local trust anchors and never committed; the `init` and `health` modes report readiness read-only. **Residual risk:** an agent running as the same account with direct database or coordinator access can still tamper; see `plugins/agent-agentic-os/skills/setting-up-agentic-os/references/isolation-setup.md`.

### 4.3. Plugin: agent-orchestration (4 skills, 13 agents)
Unified execution topologies (DAGs, supervisor/worker loops, parallel swarms via `orchestrating-agent-work`) and multi-backend task routing (`run_agent.py` to Claude, Copilot, Gemini, Agy, Codex, and direct local llama-server via `cli-agent`, plus `agt-security` sandboxing and `maf-adapter` framework validation). Includes 13 expert agent personas (architect-review, security-auditor, tdd-contract-reviewer, red-team-reviewer, etc.) which form the Phase 1 adversarial review trio per `engineering-lifecycle-policy.md` §3.

### 4.4. Plugin: agent-memory (4 skills)
Agent Memory & Knowledge combines filesystem memory, RLM summary ledgers, ChromaDB
semantic retrieval and the Obsidian vault/wiki pipeline. `memory-management` remains
filesystem-native; `managing-rlm-cache`, `managing-vector-db` and
`managing-obsidian-vaults` own their scripts, assets and references directly.
Wiki distillation and lint share one engine inside the Obsidian skill. The three-layer
wiki summary format remains distinct from RLM file-summary ledgers. Consumer profiles
stay under `.agent/learning/`; optional interoperability reads project data or uses
explicit CLI contracts rather than importing sibling skills. The skills own main-session interviews, setup, operations and Super-RAG coordination;
dedicated memory agents and command wrappers are retired. Skill-specific documents
and diagrams live under references/, with executable templates in assets/. No copy
manifest is needed by this plugin.

### 4.5. Plugin: agent-extension-authoring (6 skills)
Tooling for creating and auditing ecosystem components: `authoring-skills`, `authoring-plugins`,
`authoring-subagents`, `authoring-instructions`, `authoring-github-workflows`, and `packaging-with-apm`.
plus APM package conversion and marketplace management. Retired analyzer,
mining, standalone command, path-repair, deep-audit, and self-audit wrappers are no longer catalogued.

### 4.6. Plugin: agent-exploration-cycle (5 skills) — security-sensitive
Business discovery workflow (Path 1: pre-build discovery; Path 2: vibe-coded-prototype
migration). Backed by a hardened Python state engine in `skills/running-exploration-cycle/scripts/`: `dispatch.py`,
`state_engine.py` (SQLite, transactional, WAL), `sandbox_runner.py` (process sandboxing, HMAC-signed
envelopes, approval gating). Any change to these files requires reading `docs/ADRs/007_maf_adapter_runtime_decision.md`
first — no casual convenience bypasses to the authorization gate or path enforcement.

### 4.9. Plugin: dev-utils (8 skills)
Self-contained utilities: `managing-github-issues` (log, promote, rank, refactor proposals,
resolution audits), `resolving-github-issues` (issue worktrees and the issue-to-PR flow),
`bundling-context` (including Multi-Persona Fan-Out mode for parallel adversarial plan review),
`checking-links`, `enforcing-coding-conventions`, `managing-adrs`, `managing-symlinks` (the only
sanctioned way to create symlinks in this repo) and `managing-huggingface-assets`. The
`dependency-management` rule (pip-compile `requirements.in → requirements.txt`, no manual
`pip install`) now ships from dev-utils; the former dependency-management plugin is retired.

## 5. Architectural Rules (ADRs) — binding, not advisory

| ADR | Rule |
|---|---|
| 001 | No cross-plugin script execution — delegate via agent skill at runtime, never import another plugin's script directly |
| 002 | Within-plugin multi-skill script sharing goes through hub-and-spoke: shared scripts live in the plugin root `scripts/`, individual skills get copies from the copy manifest |
| 003 | Resource sharing uses hub-and-spoke layout, since superseded by APM packages with skills in `.apm/skills/` (no copy manifest, zero git symlinks) |
| 004 | Installed artifacts (`.agents/`, `.claude/`) must be self-contained — no runtime cross-plugin paths |
| 005 | Plugins must maintain separation of concerns and loose coupling |
| 006 | Universal Agent Package Manager (APM) replaces legacy `bootstrap.py` / `uvx` / `npx` installers |
| 007 | MAF (Microsoft Agent Framework) is an optional certified runtime adapter, never the primary orchestration kernel — `.md` manifests remain the portable source of truth across Claude Code / Copilot CLI / Gemini CLI / MAF |

Full rule text (rationale, examples, enforcement detail) lives in `.agent/rules/` — CLAUDE.md only
carries the summary. Full current set (12 consolidated rules): `engineering-lifecycle-policy.md`
(the plan/review/execution lifecycle — native Plan Mode sandboxing, bundling-context adversarial fan-out
capped at 2-3 rounds, worktree-isolated Superpowers TDD, multi-stage verification), `coding-conventions.md`,
`dependency-management.md`, `plugin-architecture-policy.md` (includes Section 5 symlink cross-platform
discipline), `self-evolution-policy.md`, `test-driven-development.md`, `destructive-action-guard.md`
(includes skill & asset deletion guards), `git-operations.md` (includes pre-push audit gates),
`github-issue-logging-policy.md`, `worktree-subagent-leak-detection.md`, `worktree-lifecycle-management.md`,
and `adversarial-reasoning-before-agreement-rule.md`.
Every file in `.agent/rules/` has a matching master under some `plugins/*/rules/` — verify with
`for f in .agent/rules/*.md; do ls plugins/*/rules/"$(basename "$f")" >/dev/null 2>&1 || echo "no master: $f"; done`.

## 6. Skill & Plugin Authoring Standards

- Skill `name`: kebab-case, matches directory name exactly, 1–64 chars.
- Skill `description`: third person.
- `evals.json`: routing criteria use `should_trigger: true/false` — the legacy `expected_behavior`
  schema silently produces 0% routing accuracy.
- `SKILL.md`: under ~500 lines; overflow detail goes to `references/`.
- Helper scripts: Python only — never bash (`.sh`).
- New plugins/skills should be scaffolded via `authoring-plugins` / `authoring-skills`, then validated with
  `authoring-plugins`, then installed and verified with `apm install` — not hand-rolled.

## 7. Resource Sharing

Each plugin is an APM package: skills, agents and hooks live under `.apm/`, and `apm install` deploys them directly. There is no copy manifest and no post-clone build step.
- No git symlinks are created. Installed skills are 100% self-contained and run on any operating system without filesystem symlink support or admin rights.

## 8. Runtime State & Memory

- `context/events.jsonl`, `context/experiment-log/`, `context/memory/` — the Agentic OS's own runtime
  state (event bus, experiment tracking, promoted memories), maintained by `agent-agentic-os` skills.
- `tasks/backlog/`, `tasks/done/` — task-tracking artifacts used by `dev-utils:task-agent` and the OS
  improvement loop.
- This is distinct from the *user's* Claude Code memory system (`~/.claude/projects/.../memory/`),
  which is a separate, cross-project persistence layer, not part of this repo's tracked state.

## 9. Deployment Model

## 9. Deployment Model

Plugins are packaged and installed using APM:

```bash
# Project installation for active client:
apm install @richfrem/<plugin-name>

# Global installation across all clients:
apm install -g --target claude,copilot,codex,antigravity @richfrem/<plugin-name>
```

This populates the target client harness (`.claude/skills/`, `.agents/skills/`, or global profiles). `build/` at the repo root is staging for APM package packaging (`apm_build_pipeline.py`), not an application build output.

## 10. Testing & Validation

- Plugin structural validation: `authoring-plugins` skill.
- Control-plane smoke tests: `plugins/agent-exploration-cycle/skills/running-exploration-cycle/scripts/smoke_test.py`.
- `agent-orchestration` router (`cli-agent`): 76+ TDD tests across scripts and contract suites.
- No single top-level test runner — tests are scoped per plugin, colocated with the plugin's
  `scripts/`.

## 12. Glossary

- **Plugin**: A directory under `plugins/` bundling related skills, agents, commands, and scripts around one capability area.
- **Skill**: A `SKILL.md`-defined capability, self-contained, no runtime cross-plugin dependencies.
- **Bridge installer**: The legacy installer (superseded by native APM package distribution).
- **RLM**: Dense-summary keyword cache used for fast O(1) file lookup (agent-memory plugin).
- **MAF**: Microsoft Agent Framework — optional certified runtime adapter per ADR-007, not the primary kernel.
- **Control plane**: The SQLite/HMAC-hardened state and sandboxing layer in agent-exploration-cycle (`state_engine.py`, `sandbox_runner.py`, `dispatch.py`).
